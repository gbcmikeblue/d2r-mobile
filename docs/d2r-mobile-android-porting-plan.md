## 1. 项目目标与范围

### 1.1 目标

在 Android ARM64 设备上建立可验证的运行路径，逐步实现：

1. 编译并加载原生运行时。
2. 复用项目中与平台无关的逻辑。
3. 适配 Android/Linux 环境下所需的 Host 能力。
4. 实现 Vulkan 图形后端及所需的 Shader 转换路径。
5. 接入 Android 应用生命周期、输入、音频、存档和资源管理。
6. 在真实设备上验证功能、稳定性、性能与兼容性。

### 1.2 非目标

初期不建议同时进行以下工作：

- 不同时升级游戏版本、重写指令改写规则和更换多个核心依赖。
- 不在 Vulkan 关键路径尚未验证时投入大量 UI 美化工作。
- 不以“APK 能安装”作为移植成功的判断标准。
- 不在缺乏证据时将崩溃归因于单一驱动、USB 连接或某个 API。
- 不将受版权保护的游戏资源打包进公开发布的构建产物。

### 1.3 核心判断

这不是简单的 iOS 工程重新编译。即使目标程序与 Android 设备都使用 ARM64，也不代表 Switch 运行环境的系统调用、线程语义、内存管理、图形 API 和资源格式能直接兼容。

主要工作分为三类：

- **可复用逻辑**：游戏版本处理、部分指令分析与改写、资源处理工具、平台无关的兼容层代码。
- **平台适配**：Host、线程、内存、文件、计时器、输入、音频与应用生命周期。
- **重点重写**：与 Metal 深度耦合的图形后端，以及无法直接复用的 Shader 转换流程。

以上分类是审计起点，不是对仓库每个文件的既定结论。应以源码依赖和构建结果确认。

## 2. 推荐总体架构

```text
游戏原始 ARM64 程序与资源
             |
             v
   现有程序处理/兼容层
             |
             v
   Host 兼容层与系统服务
      |                 |
      |                 +--> 线程 / TLS / 内存 / 文件 / 同步
      |
      v
     NVN API 兼容层
             |
             v
     图形后端抽象接口
        |           |
        v           v
   原有 Metal     新增 Vulkan
        |           |
        v           v
      iOS         Android NDK
                      |
                      v
              JNI / Activity / UI
```

### 2.1 目标代码分层建议

在审计原工程后，可考虑形成类似结构：

```text
dm/
├── host/
│   ├── common/       # 经验证的平台无关代码
│   ├── posix/        # 经验证可复用的 POSIX 实现
│   └── android/      # Android 特有实现
├── gfx/
│   ├── common/       # 公共资源和状态管理
│   ├── nvn/          # NVN API 兼容逻辑（按原仓库实际结构调整）
│   ├── metal/        # 原 Apple 图形后端
│   └── vulkan/       # 新增 Vulkan 后端
├── ios/              # 保留原有 iOS 应用
└── android/          # 新增 Android 应用
```

这是建议的目标布局，不表示仓库当前已经有这些目录。不要为了匹配该结构而大规模搬动代码；优先采用小步提交、保持现有构建可回归的方式。

## 3. 开始前：仓库与构建基线

### 3.1 固定基线

开始修改前记录：

- Git commit ID、分支与工作区状态。
- 游戏版本与资源版本。
- macOS/Linux/Windows 版本。
- 编译器、CMake、Ninja、Python、LLVM 等工具版本。
- 当前项目的构建方式、依赖下载方式和许可证。
- 原项目已知问题及可复现步骤。

建议保存以下信息：

```bash
git rev-parse HEAD
git status --short
git submodule status
```

如果项目使用其他依赖管理工具，也记录其 lockfile 和依赖版本。

### 3.2 阅读关键文档和目录

优先检查仓库中是否存在并阅读：

- `README.md`
- `dm/README.md`
- `dm/host/README.md` 或 Host 相关说明
- `dm/gfx/README.md`
- `dm/ios/README.md`
- `dm/verify/` 中的验证说明
- `docs/DEPENDENCIES.md` 或同类依赖文档
- CMake、Makefile、脚本和 CI 配置

目录和文件名可能随版本变化。若路径不存在，应通过仓库搜索找到实际位置，不要直接照抄本文中的路径。

### 3.3 执行原有测试

只有在确认当前仓库存在相应目标后再执行。示例命令如下：

```bash
make -C dm/host/tests run
make -C dm/gfx/tests run
dm/verify/regress.sh
```

若命令不存在或需要额外环境，先查看 README、Makefile 和脚本头部，按项目当前说明执行。

### 3.4 基线验收标准

- 原项目在未修改状态下可按文档构建。
- 原有单元测试和回归测试结果已记录。
- 至少有一条可重复的原平台运行/验证路径。
- 关键工具链版本固定。
- Android 工作放在独立分支，不破坏原有 iOS 路径。

**高风险坑 01：基线不稳定。** 如果原项目在修改前就无法构建或测试不稳定，后续 Android 失败无法可靠归因。应先区分原有问题与新增问题。

**高风险坑 02：版本漂移。** 移植期间同时更换游戏版本、指令改写规则、编译器和 Shader 工具，会大幅增加排障成本。一次只改变一个主要变量。

## 4. 阶段一：源码审计与平台边界拆分

### 4.1 建立文件依赖清单

对每个关键源文件记录：

| 字段 | 内容 |
|---|---|
| 文件/模块 | 源码路径 |
| 当前职责 | Host、图形、输入、工具、UI 等 |
| Apple 专属依赖 | Metal、Objective-C/Swift、Apple SDK 等 |
| 可复用程度 | 可直接复用 / 需小改 / 需重写 / 待确认 |
| 调用方 | 谁调用它 |
| 测试方式 | 单测、集成测试、真机测试 |
| 风险等级 | 高 / 中 / 低 |

搜索 Apple 专属依赖时，可以使用：

```bash
grep -RInE 'Metal|MTL[A-Za-z]+|UIKit|AppKit|Foundation|Objective-C|\\.mm$' dm
```

该命令只适合初筛，可能漏掉间接依赖或产生无关匹配。也要检查构建文件、条件编译、链接参数和第三方库。

### 4.2 拆分原则

1. 先识别平台边界，再设计抽象接口。
2. 尽量保持原有 NVN API 兼容层的外部行为不变。
3. 将平台相关实现放在独立模块，避免 Android 条件编译散布到整个工程。
4. 新增接口时为原平台保留实现，避免移植过程破坏 iOS。
5. 每个重构步骤都应能单独编译或通过对应测试。

**高风险坑 03：过早抽象。** 不要一开始就建立庞大通用接口或重写所有模块。应先通过依赖图和真实调用确认需要抽象的边界。

## 5. 阶段二：Android 工程与工具链

### 5.1 推荐工具

- Android Studio
- Android SDK
- Android NDK（版本应与项目依赖和 CMake 配置相容）
- CMake
- Ninja
- Clang/LLD（通常由 NDK 提供）
- ADB、Logcat
- LLDB 或其他 Android 原生调试工具
- Vulkan Validation Layers（开发调试时，设备支持的情况下）
- Perfetto、Android GPU Inspector 或厂商 GPU 工具（适用时）

先以 `arm64-v8a` 为首个目标 ABI。不要在初期同时处理多个 ABI，除非项目本身有明确需求。

### 5.2 建立最小 Android Native 原型

第一步不接入完整游戏，只完成：

1. APK 安装与启动。
2. 加载一个 Native 库。
3. JNI 调用可用。
4. 日志可输出。
5. Activity 进入后台和返回前台时行为明确。
6. 设备信息、ABI 和 Vulkan 能力可以被记录。

### 5.3 构建配置注意点

- 确认 Android API Level 与使用的 NDK API 相容。
- 确认 Native 依赖能被打包进 APK，且动态链接器可找到。
- 检查 C++ 标准、异常、RTTI、链接参数和第三方库的 ABI。
- 不要直接复制 iOS 的编译选项和链接参数。
- 避免将宿主机生成的二进制误打包进 Android APK。
- 将调试构建和发布构建分开。

**高风险坑 04：APK 能安装不等于 Native 能运行。** ABI 不匹配、缺失动态库、JNI 签名错误或错误的打包路径都可能导致启动即闪退。

## 6. 阶段三：Host 兼容层

Android 使用 Linux 内核并提供 POSIX 类接口，但并不等于实现了 Switch Horizon OS 的所有行为。应根据程序实际依赖逐项验证。

### 6.1 审计清单

| 领域 | 需要验证的内容 | 常见故障 |
|---|---|---|
| 线程 | 创建/退出、优先级、线程局部状态 | 随机崩溃、死锁 |
| TLS | 线程指针、TLS 布局与访问方式 | 运行早期崩溃、数据错乱 |
| 系统调用 | 编号、参数、返回值和错误语义 | 初始化失败、非法访问 |
| 内存 | 地址映射、权限、对齐、共享内存 | 崩溃、资源损坏 |
| 同步 | Mutex、Event、Semaphore、等待/唤醒语义 | 永久等待、竞态 |
| 计时器 | 单调时钟、精度、超时语义 | 逻辑卡顿、异常帧率 |
| 文件系统 | 路径映射、只读资源、存档写入 | 资源找不到、保存失败 |
| 异常/信号 | 故障捕获、调用栈、退出路径 | 无法定位的 Native 崩溃 |
| 动态加载 | 库加载、符号解析、内存权限 | 启动失败 |
| 网络/IPC（若使用） | socket、共享内存、进程间通信语义 | 服务初始化失败 |

### 6.2 实施方法

1. 找出 Host 入口和初始化调用顺序。
2. 为每项系统服务列出原有语义、Android 实现和差异。
3. 对线程、TLS、内存映射、计时器和同步原语优先写独立测试。
4. 使用最小程序验证每项行为，避免依赖整个游戏才能复现。
5. 为失败路径加入结构化日志和错误码。
6. 再将验证过的实现接入游戏启动流程。

### 6.3 验收标准

- Host 可在 Android 中独立初始化。
- 线程创建、销毁、TLS 和计时器测试通过。
- 资源可以通过 Android 文件接口读取。
- 可控故障能输出原生调用栈和模块信息。
- 测试不依赖 Metal 或 iOS UI。

**高风险坑 05：机械替换系统调用。** 相同的 ARM64 指令集不意味着操作系统 ABI 相同。必须对照实际参数、寄存器约定、返回值、线程局部状态、信号和内存权限行为，不应只按函数名称替换。

## 7. 阶段四：Vulkan 图形后端

这是整体移植的高风险核心。不要将它当作 Metal API 的一对一替换工作。

### 7.1 分三步推进

#### 里程碑 A：独立 Vulkan 最小程序

在 Android 真机上实现：

- Vulkan Instance 与物理设备枚举。
- Surface 与 Swapchain 创建。
- 清屏和三角形绘制。
- 窗口旋转、Surface 销毁与重建。
- Activity 暂停和恢复。
- 设备能力与扩展枚举。

此时不接入游戏。目的是验证 NDK、Vulkan、Surface 和 GPU 驱动的基本路径。

#### 里程碑 B：图形资源与命令映射

基于源码实际使用的 NVN API，逐项映射：

- Buffer、Image/Texture 和内存分配。
- 资源格式与布局。
- Pipeline、Shader 模块与 Descriptor。
- Command Buffer 与提交。
- Fence、Semaphore 及队列同步。
- Render Pass 或动态渲染路径（根据项目需求与设备支持选择）。
- 深度、模板、混合、采样和光栅化状态。
- Swapchain 生命周期与图像布局转换。

不要先追求覆盖所有 API。优先实现游戏启动和主菜单所需的最小调用子集，并以实际调用日志为依据扩展。

#### 里程碑 C：Shader 转换与真实场景

首先弄清原项目的 Shader 流程：

1. 输入 Shader 的格式是什么。
2. 哪些阶段由项目自己的工具处理。
3. 哪些阶段依赖 Metal 编译器或 Apple 专属工具。
4. 中间表示是否可复用。
5. 是否能生成 Vulkan 可使用的 SPIR-V。
6. Descriptor、Uniform、Push Constant、纹理和采样器布局如何保持一致。

如果有可复用的中间表示，可评估转换为 SPIR-V 的路径；若转换链深度依赖 Metal 特性，则需要为相应语义设计独立实现。不能假定 Metal Shader 可以直接交给 Vulkan 使用，也不能假定 SPIR-V 编译成功就代表渲染结果一致。

### 7.2 高风险坑

**坑 06：GPU 资源生命周期与同步**

- 明确每个资源的创建、使用、同步和释放时机。
- 确认命令提交和资源读写依赖。
- 检查 Fence、Semaphore、队列和 Swapchain 图像状态。
- 避免在 GPU 尚未完成使用时释放资源。
- 不要把所有同步问题都通过增加延时或等待来掩盖。

**坑 07：Shader 与 Descriptor 不一致**

绑定编号、Uniform 布局、Buffer 对齐、纹理格式或采样状态不匹配，可能造成黑屏、贴图错乱、深度错误或只在特定场景发生的故障。

**坑 08：Metal 与 Vulkan 语义差异**

不能只将相似名称的函数互相替换。需要验证渲染状态、资源布局、同步、采样、混合、深度和命令执行语义。

**坑 09：设备扩展与纹理格式差异**

不同 Android SoC/GPU 支持的格式、扩展和性能不同。启动时应检测实际能力；对必要功能设计经验证的回退路径。不要假设所有 Android 设备都具有同样的 Vulkan 功能集。

**坑 10：过早优化性能**

先确保画面正确、同步正确和运行稳定，再优化帧率。过早引入缓存、异步编译和复杂的资源复用，会增加定位错误的难度。

### 7.3 图形后端验收标准

| 项目 | 验收要求 |
|---|---|
| API 与资源 | 资源创建、释放和重建可重复运行 |
| Shader | 关键 Shader 编译成功，接口布局正确 |
| 渲染 | 角色、地面、透明特效、UI 等关键元素正确 |
| 同步 | 长时间运行无可复现的随机闪屏、死锁或资源竞争 |
| 场景切换 | 地图切换和退出流程正常 |
| Validation | 开发环境中无未解决的关键 Vulkan 使用错误 |
| 真机 | 至少完成目标设备上的实际游戏场景测试 |

Validation Layers 只能帮助发现部分 API 使用错误，不能证明渲染语义正确，也不能覆盖所有驱动问题。

## 8. 阶段五：Android 应用层

推荐以 C/C++ Native 运行时为核心，通过 JNI 连接 Kotlin/Java 应用管理层。

### 8.1 主要功能

- Native 库加载、初始化和退出。
- Vulkan Surface 创建、销毁与重建。
- 游戏主循环与线程管理。
- 触控、虚拟摇杆、技能按键和手势。
- 蓝牙/USB 手柄（按项目需求）。
- 音频初始化、输出与暂停恢复。
- 游戏资源导入和路径管理。
- 存档持久化。
- Activity 生命周期管理。
- 崩溃日志、版本信息与诊断导出。

### 8.2 生命周期处理

必须覆盖：

- Activity 创建和销毁。
- 应用切后台与返回前台。
- 屏幕旋转或窗口尺寸变化。
- Surface 被销毁后重建。
- 音频设备变化或音频焦点丢失。
- 进程被系统回收。
- 用户退出游戏。

**高风险坑 11：Activity 与 Surface 生命周期不相同。** Surface 被销毁后，渲染线程不得继续向旧 Surface 提交工作。重建时需要按正确顺序重建与 Surface 相关的 Vulkan 对象。

**高风险坑 12：UI 线程承担过多工作。** 游戏循环、GPU 提交、文件 I/O 和音频工作应有清晰线程职责。否则容易出现 ANR、音频断续和退出死锁。

**高风险坑 13：存储权限与路径假设。** Android 不能照搬 iOS 的文件访问方式，也不能假设 APK 旁存在可写目录。建议使用系统文件选择器导入用户有权使用的游戏资源，并为存档设置明确的应用私有持久化目录。

**高风险坑 14：暂停恢复与存档一致性。** 测试进程被回收、设备锁屏、应用切换和异常退出时的行为；确保存档写入不会留下半截文件，必要时采用临时文件加原子替换等策略。

## 9. 分级测试计划

不要把“能启动”当作移植完成。建议按以下关卡逐步验收：

| 级别 | 测试内容 | 通过标准 |
|---|---|---|
| L0 | 构建与安装 | APK 安装，Native 库成功加载 |
| L1 | Host | 线程、TLS、内存、计时器和文件测试通过 |
| L2 | Vulkan 基础 | 清屏、三角形、Swapchain 重建正常 |
| L3 | 游戏主菜单 | 程序运行，UI 与关键 Shader 正常 |
| L4 | 第一个实际场景 | 角色、地图和资源加载成功 |
| L5 | 完整核心循环 | 移动、攻击、怪物、技能与特效可用 |
| L6 | 生命周期 | 暂停、恢复、退出、重启和存档正常 |
| L7 | 稳定性 | 长时间运行、切场景和内存压力测试通过 |
| L8 | 性能 | 记录帧率、帧时间、内存、温度和功耗表现 |

每一级都应保存测试步骤、设备型号、系统版本、日志、通过/失败状态和相关提交 ID。出现回归时，优先找出首次失败的级别。

### 建议的测试设备策略

- 第一台设备：目标 GPU 与 Vulkan 能力明确的 ARM64 Android 手机。
- 第二台设备：不同 SoC/GPU 的 Android 手机。
- 先固定一个设备完成主路径，再逐步扩大设备覆盖。
- 不要只使用 Android 模拟器判断真实 GPU 后端是否可行。

## 10. 故障排查手册

| 现象 | 优先排查 | 不建议先做 |
|---|---|---|
| APK 一启动就闪退 | ABI、动态库、JNI、Native 调用栈 | 重写 Vulkan |
| Host 初始化失败 | 系统调用、TLS、内存映射、线程 | 直接修改游戏二进制 |
| 主菜单黑屏 | Vulkan 初始化、Shader、Swapchain、资源绑定 | 优先优化帧率 |
| 角色/地图贴图异常 | Shader、纹理格式、Descriptor、采样状态 | 盲目换驱动 |
| 进入战斗后卡死 | GPU 同步、线程死锁、资源生命周期 | 单纯增加超时 |
| 随机闪退 | 内存越界、竞态、驱动错误、资源释放 | 只在崩溃处加重试 |
| 运行后逐渐降帧 | 热降频、CPU/GPU 瓶颈、内存压力 | 一开始就降低画质 |
| 切后台后黑屏 | Surface 生命周期、Swapchain 重建、线程状态 | 忽略恢复流程 |
| 退出时卡死 | 线程 join 顺序、GPU 等待、音频退出 | 强制结束所有线程 |

### 10.1 `VK_ERROR_DEVICE_LOST` 的处理原则

不要把 `VK_ERROR_DEVICE_LOST` 从诊断或错误处理逻辑中删除。它表示 Vulkan 设备已丢失或无法继续正常使用，可能与驱动崩溃、非法 GPU 操作、设备重置或硬件环境有关。它不一定是根因，但不应被当作普通可忽略错误。

建议：

1. 记录发生错误的 Vulkan 调用、设备信息和前序 GPU 操作。
2. 在开发环境尽可能启用 Validation Layers，并保存 Logcat/原生日志。
3. 确认是否与特定 Shader、场景、资源释放或同步操作稳定相关。
4. 将 USB 连接、设备重启等外部事件记录为环境信息；没有证据时不要直接认定其为根因。
5. 设计明确的失败路径：哪些情况可重建设备，哪些必须终止当前渲染流程。
6. 设备丢失后，不要假设原来的 GPU 资源、队列和同步对象仍可正常使用。

### 10.2 日志建议

统一记录：

- 时间戳、线程 ID、模块名和日志等级。
- 初始化阶段与当前测试关卡。
- Android 版本、设备型号、ABI、GPU 名称和 Vulkan 能力。
- 关键资源创建/释放、Shader 编译和队列提交事件。
- 原生崩溃调用栈、信号和错误码。
- Git commit、构建类型与应用版本。

避免在高频渲染路径中无节制输出日志，以免影响性能和时序。

## 11. 工作量估算

以下是工程规划区间，不是对当前仓库状态的实测承诺。假设由一名熟悉 C/C++、Android NDK 和图形 API 的开发者独立实施。

| 阶段 | 粗略估算 | 主要不确定性 |
|---|---:|---|
| 基线验证与源码审计 | 3–7 天 | 依赖、构建环境、文档完整性 |
| Host 平台适配 | 1–3 周 | 系统调用、TLS、内存与同步 |
| Vulkan 基础后端 | 2–4 周 | API 语义、资源管理和同步 |
| Shader 转换与真实场景 | 3–8 周以上 | 工具链、格式与驱动差异 |
| Android 应用层 | 1–3 周 | 生命周期、输入和音频整合 |
| 真机测试与优化 | 2–6 周以上 | 设备覆盖、稳定性和性能 |

部分工作可并行，不能简单将各区间下限相加作为最终工期。

粗略规划：

- **技术验证原型**：约 2–6 周，目标是验证关键路径，不保证进入完整游戏。
- **可进入实际游戏场景的实验版本**：约 2–4 个月，前提是代码复用率较高且 Shader 迁移顺利。
- **相对稳定的日常游玩版本**：约 4–9 个月或更久，取决于图形后端复杂度、设备覆盖与缺陷数量。

如果图形后端与 Metal 耦合很深，实际工作量可能显著超过以上区间。建议在完成源码审计和 Vulkan/Shader 可行性验证后再调整计划。

## 14. 开发纪律与决策原则

1. **先证实，再扩展。** 先验证最小路径，再扩大 API 覆盖。
2. **保持可回归。** 每个提交尽量只改变一个主要变量。
3. **不掩盖错误。** 不删除关键错误、不用无条件重试掩盖同步或资源问题。
4. **以日志和复现为依据。** 对每个问题保留最小复现步骤。
5. **先正确，再优化。** 画面、同步和稳定性通过后再优化性能。
6. **真实设备优先。** 模拟器不能替代真实 GPU 驱动测试。
7. **明确支持范围。** 先支持少量经过验证的设备与系统版本，再扩大范围。
8. **保护原有平台。** 保持 iOS 路径可构建、可测试。
9. **记录技术债务。** 临时 workaround 必须标明原因、影响和移除条件。
10. **尊重软件与资源许可。** 分别审查代码依赖、游戏资源和分发产物的授权要求。

## 16. 结论

建议采用以下顺序：

1. 固定原项目基线并完成文件级审计。
2. 建立 Android Native 原型。
3. 独立验证 Host 的线程、TLS、内存与系统调用。
4. 独立验证 Vulkan Surface、Swapchain 和基础渲染。
5. 确认 Shader 转换链可行，再实现关键 NVN API 映射。
6. 接入游戏主菜单和第一个真实场景。
7. 补齐输入、音频、存档与生命周期。
8. 在真实设备上进行稳定性、兼容性和性能回归。

**最大的项目风险不是 APK 工程本身，而是 Host 的系统语义兼容，以及 Metal 后端与 Shader 工具链迁移。** 应尽早验证这两项；只有它们通过，后续 UI、输入和发布流程的投入才更有把握。
