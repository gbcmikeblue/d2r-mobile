## B′. N0 期间量出来的仪器事实（2026-10-16，下次开工直接用）

这些不是设计，是**用探针在真机上问出来的**；开工前不必再试一遍：

| 事实 | 读数 / 怎么用 |
|---|---|
| **"一档尺寸一个进程"在 Android 上不用 shell 就能做** | `vk2_probe` 用 `posix_spawn` **复执行 `/proc/self/exe`**（子进程模式：`vk2_probe size <MB>`），父进程从子进程 stdout 里取 `RESULT` 行 ⇒ 不必写 shell 包装，也不必担心"一次失败带坏同进程之后的小分配"（AHB 探针踩过）|
| **`posix_spawn` 把子进程 stdout 接进管道** | `pipe()` + `adddup2(fa, p[1], 1)` + `addclose(p[0])` + `addclose(p[1])`（**按这个顺序**），父进程读到 EOF 再 `waitpid`；`/proc/self/exe` 可读、`posix_spawn` 可用 |
| **解析子进程输出：先解析、后分词** | `strtok_r` 会把 `\n` 换成 `\0`，换过之后 `strstr(buf, …)` **只能看到第一行**（N0 第一轮就被这个骗了：子进程明明打了 `RESULT`，父进程报"没打"）|
| **重录命令缓冲必须带池标志** | 池上要 `VK_COMMAND_POOL_CREATE_RESET_COMMAND_BUFFER_BIT` + 每次 `vkResetCommandBuffer`；否则在非初始态 cb 上 `vkBeginCommandBuffer` 是未定义行为，实测表现是"**跑到第 31 条时 `vkQueueSubmit` 开始返回 `-3`**"，读数长成"684 MB/s、中途有提交/等待失败"，**看着像驱动的锅**。加上之后同一段变成 256 条、156~170 ms、零失败 |
| **栅栏可以带超时地等，而且能恢复** | 对未置位栅栏 `vkWaitForFences(…, timeout=0)` → **`VK_TIMEOUT`**（VkResult 2，如规范所期）；超时之后**同一栅栏**在提交后能等到成功 ⇒ N3 的"有界在飞 + 带超时等栅栏"不需要额外能力 |
| **`DEVICE_LOCAL` 分配是惰性的** ⚠**已被 N1 更正**（原文保留） | 建 1024 MB 缓冲 + 四点填充后 `MemAvailable` 只掉 **2~7 MB**（未碰的页不提交）⇒"块建出来了"≠"占着物理内存"。**【更正（N1）】**：5 块 × 960 MB（4 GB）时**后备资源掉 4080 MB**（7230 → 3150 MB，四轮一致），而 4 GB 匿名 mmap 掉 **0 MB** ⇒ 这句话**不能当结论**，池预算按"后备资源字节数"算；N2 再量一次。详见 `ANDROID_PLAN` §八·N1 |
| **超过 `maxMemoryAllocationSize` 的分配会"看着成功"** | 1088 MB 那一档：建 / 分配 / 绑定 / 提交全 `VK_SUCCESS`，**尾页 4 KB 回读对不上**（三轮一致）⇒ 凡"建出来了"的判据都要含"**头尾都真写一遍并回读**"，别只看 `vkAllocateMemory` 的返回值 |
| **探针输出要分段可辨** | 每个问题一行 `[问 n]` + 若干 `[答] …`，末尾一段 `--- KEY=VALUE ---`；一档一进程时父进程把子进程整段**原样缩进回显**（`  | …`）⇒"这一问真的问了没、答是什么"在读数文件里一眼可查 |

## B″. N1 期间量出来的仪器事实（2026-10-16，下次开工直接用）

| 事实 | 读数 / 怎么用 |
|---|---|
| **`malloc` 的指针最高一个字节带标记（TBI）** | 实测 `VK2_POOL_MALLOC_TAG_BITS = 0xb400000000000000`，而 `mmap` 与 `/proc/self/maps` 给的是**不带标记**的地址 ⇒ **凡"拿地址去和 maps 比"的地方都要先掩掉最高那个字节**（硬件忽略位 56~63）。掩 48 位是宿主 `crash.c` 给 **PAC 返回地址**用的另一套（签名占高 16 位），两者别混：52 位 VA 的设备上位 48~51 是真地址。**不掩的后果**：真实池子被判成"不是普通内存"（N1 第一版就栽在这里，`no_region` 变成 2、`malloc` 池登记失败） |
| **判"这段地址是不是普通内存"要能把账打出来** | 判法是"`/proc/self/maps` 里必须有一段 `rw` 把 `[lo, hi)` 整段盖住"；判失败时**必须同时打**：共读了多少行、解析出多少行、第一行结束位置超过池首的映射是哪一行、最后一行。（这条是 N1 能一次定位到 TBI 的原因——只报一句"不是普通内存"会让人去怀疑判法本身） |
| **4 GB 匿名 mmap 便宜，后备资源才吃内存** | `MAP_NORESERVE` 的 4 GB 池内存只碰三个字节 ⇒ `MemAvailable` 掉 **0 MB**；而 5 块 960 MB 的 `DEVICE_LOCAL` 后备资源掉 **4080 MB**（7230 → 3150 MB，四轮一致）⇒ **池预算按后备资源字节数算**（← 同时更正了 N0 的"惰性提交"） |
| **建块的耗时形状** | 首块 **5610 µs**（含命令缓冲 / 首次提交预热），之后每块"头页 + 尾页各填一遍再回读"**501~700 µs** |
| **反查本身很便宜** | 199998 次 `vk2_addr`（含跨块分支与日志节流）**4 ms** ⇒ 反查不会是帧预算的瓶颈；跨块日志必须节流（前 16 条明细，其余只计数） |
| **`__DATE__ / __TIME__` 只能证明"那一个编译单元"的编译时刻** | 改 `vk2_pool.c` 只会重编那个 .o 并重新链接，**探针自己那行 `构建：…` 的时分秒不会变** ⇒ **不能用它判断"设备上跑的是不是最新构建"**（本次一度被它骗过：看着像"没重编"，其实新的 .c 已经进去了）。要判就看本地产物 / `.o` 的 mtime，或让**被改的那个文件**打自己的版本串 |
| **多轮跑法已经脚本化** | `.work/vk2_pool_rounds.py --rounds 4`：第 1~N−1 轮带 tag 留档、**最后一轮不带 tag = 正式读数**，末尾打一张"字段 × 轮次"的对照表（哪个字段轮间不一致一眼看出来）。N1 四轮全部 29 个字段完全一致 |
| **`.work/probes.py`（重建）** | 本次会话开工时这台机的 `.work/` 里缺了那批脚本（`.work` 不进仓库、换机器就要重建）⇒ 按文档里的接口重建了 `probes.py`（`build` / `push` / `run`，带 `--env` / `--tag` / `--serial`）。两处照规矩办：`adb shell` 的复合命令**整条当一个字符串传**；读数文件名固定 `probe-<串号>-<探针名>[-tag].txt` |
| **探针的"一问一答 + 末尾 KEY=VALUE"这套形状很好用** | N1 探针六问：`[问 n]` / `[答]` / `[池]`（模块自己的日志）/ 末尾 `--- VK2_POOL_SUMMARY ---`。四轮之间逐字段对比，比"看日志感觉差不多"可靠得多 |

## B‴. N2 期间量出来的仪器事实（2026-10-16，下次开工直接用）

| 事实 | 读数 / 怎么用 |
|---|---|
| **「一条 run 比暂存环还大」是必须处理的形状** | 512 MB 的搬运被 16 MiB 环切成 **32 个窗口**；切片条件必须是 `min(块内余量, 环余量)` —— 只按块边界切，会让"整条 run 大于环"变成**整个窗口被拒**（第一版就栽在这里：读数长成 `0 个窗口 / 0 MB`）。切片后：搬完的页置 CLEAN、剩下的仍是脏，下一窗口继续 |
| **位图三态要两位** | 4 GB 池 = 1048576 页 ⇒ CPU/GPU 各一张 1 bit 位图 = **262144 字节**（N0 量的 131072 是"1 bit/页"的账，三态翻倍）。扫描耗时：**空池 21~47 µs**（整字跳过一个 64 位字 = 64 页）、**稀疏（1% 页 = 10485 页脏）1051~1674 µs / 10313 条 run**、**全脏 1593~1782 µs / 1 条 run** ⇒ 4 KiB 粒度**维持**（扫描不是瓶颈，"并 run"把全脏压成 1 条） |
| **「等栅栏」与「看得见」是两件事** | G2 的读数：**等栅栏成功之后** CPU 那份副本**仍是旧值**（65536/65536 字节）；只有显式回读才变新值 ⇒ 任何"等完就该看到"的假设在 Vulkan 上都是错的。这条同时是**排除法**：以后遇到"读到旧值"，先看有没有真的回读 |
| **首次提交有预热** | 第一个窗口的"提交+等栅栏"是 **5.9~7.2 ms**，之后 **519~717 µs**（与 N1 建块首块 5610 µs 同源）⇒ 报读数时**首窗口要单独标出来**，否则会被读成"每次提交都 6 ms"。回读一次 64 KiB 在 **200~230 µs**（含两次提交 + 两次等待） |
| **半页竞态会被真的触发** | 一轮 20000 次随机记账里命中 **5225 次（26%）**（只由随机测试的形状决定，不是游戏的形状）⇒ 规则不是摆设，N4 的绑定点上必须有对策（先回读该页 / 页内字节级记账）；同时它**必须节流**（每命中一次打一行 = 一轮 5225 行，会把读数淹掉，改成前 8 条明细） |
| **把纪律做成编译期就挡得住的东西** | `vk2_xfer.c` 里把 `vkQueueWaitIdle` **宏成"计数 + 报红"**：谁以后手滑写上一句，计数不会静默为 0（G4 的判据就是它恒 0）。比"代码 review 时记得看一眼"牢靠 |
| **对照表脚本能带探针参数了** | `.work/vk2_pool_rounds.py --probe vk2_xfer_probe --rounds 4`：同一套"前 N−1 轮带 tag、最后一轮不带 tag = 正式读数 + 字段对照表"跑任意探针；键值并集里某个探针不产的键会被跳过 |
| **判据字段与时间字段要分开看** | N2 四轮里**所有判据字段逐轮完全一致**，抖动的只有六个时间字段（空池扫描 21~47 µs、稀疏 1051~1674 µs、全脏 1593~1782 µs、贴图单段 3.3~14.0 ms、贴图 64 段 1.6~2.3 ms、512 MB 真搬 127~153 ms）⇒ **报区间，不报单值** |

## B⁗. N3 期间量出来的仪器事实（2026-10-16，下次开工直接用）

| 事实 | 读数 / 怎么用 |
|---|---|
| **量"有界在飞该取几"必须为每一档把 GPU 塞满** | 空提交时 D=3/4/8 的差别只有几十 µs（N0 的读数），**分辨力不够**；每次提交里录一段 ~128 MB 的设备内拷贝之后：D=1 每提交 **7822~13587 µs**、D≥3 **4059~4085 µs** 才看得出深浅 ⇒ 合成测试的"GPU 活"大小就是它的分辨力 |

## B⁷. N4-c 期间量出来的仪器事实（2026-10-16，下次开工直接用）

| 事实 | 读数 / 怎么用 |

## G. 真机装 Vulkan 校验层（配方 + 脚本，2026-10-16 在第一台 Adreno 830 / Android 16 上跑通）

**一句话**：层 `.so` 放进 APK 的 `lib/arm64-v8a/`，再 `adb shell setprop debug.vulkan.layers VK_LAYER_KHRONOS_validation`
—— **不用 root、不用改一行代码**（清单里的 `android:debuggable="true"` 是这件事的前置，本项目早就写着）。

| 环节 | 做法 / 读数 |
|---|---|
| **先量能力**（别盲改） | `.work/vallayer_probe.py`：`getprop debug.vulkan.layers`（空）、`setprop` 后能否读回（**能**，shell 有权限）、`dumpsys package <pkg>` 的 flags 里有没有 `DEBUGGABLE`（**有**）、`cmd gpu vkjson` 的**实例级** `apiVersion`（**4210688 = 1.4.0** ⇒ 与 1.4.363 的层兼容；设备级 `4206876 = 1.3.284` 是驱动、不是 loader） |
| **layer 放哪** | 安卓的 loader 只从 **app 私有的 native 库目录**找层。先量过这个前提：`/data/app/~~…/<pkg>-…/lib/arm64/` 里**确有抽取出来的 `libdm.so`**（说明本包走的是 `extractNativeLibs=true` 那条路）⇒ 层放同一个目录就能被 `opendir` 扫到 |
| **进包** | `dm/android/apk/build_apk.cmd` 里**一个缺省关的可选段**：`DM_VKLAYER=1` 才把层按 NoCompression 加进 `lib/arm64-v8a/`（不设时整段不出现、常态包逐字节不变；用 4 KB 占位 .so 验过两次） |
| **怎么取层** | 只有 GitHub release 一个来源：`…/releases/download/vulkan-sdk-1.4.363.0/android-binaries-1.4.363.0.zip`（**32,748,819 字节**，里面的 `arm64-v8a/libVkLayer_khronos_validation.so` = **27,684,688 字节**）。⚠ **GitHub API 会 403 rate limit**（匿名配额），走 HTML / 直链；⚠ **本机走 HTTPS 代理**，`curl` 必须带 `--connect-timeout 20 --max-time 1800 --retry 5 --retry-all-errors --speed-limit 2048 --speed-time 60 -C -`（实测在 26 MB 处断一次，续传才完）；⚠ `urllib` 对 github.com 会 `IncompleteRead`（32768 / 65536 / 262144 字节处截断）⇒ **别用它下 GitHub 的东西** |
| **启用与自证** | `adb shell setprop debug.vulkan.layers VK_LAYER_KHRONOS_validation` + 读回；层活着的**硬证据**在 logcat：`added global layer 'VK_LAYER_KHRONOS_validation' from library '/data/app/…/lib/arm64/libVkLayer_khronos_validation.so'` 与 `Loaded layer VK_LAYER_KHRONOS_validation`（**"0 条"= 没加载，">0 条"= 活着**，这是判据，别用"有没有报错"当"有没有加载"） |
| **怎么收消息** | 层用 `__android_log_print`（tag `VALIDATION`）**和** stderr 各打一遍 ⇒ logcat 里每条消息出现两次（第二次的 tag 是我们自己的 `dmhost`）⇒ **按 `MessageID` 去重**再统计 |
| **一轮怎么跑** | `.work/vklayer_round.py --conf <conf> --tag <tag> --secs 45 --build --install`：出包（带层）→ 装机 → 设属性 → **`logcat -c` 后起一个 logcat 抓取进程** → 启动 app → 跑 → 停抓取 → 拉我们的日志 → **清属性回退**。读数落 `.work/logs/logcat-<tag>.txt` 与 `n4-<tag>.log` |
| **退回常态** | `.work/vklayer_off.py`：出干净包（不带 `DM_VKLAYER`）→ 装机 → 清属性 → 打 `nativeLibraryDir` 清单自查（应当只剩 `libdm.so`） |

**读 logcat 的三个坑**（都是本轮踩的）：

1. **`Validation Error: [ VUID-… ] | MessageID = 0x…` 只是首行**，"具体原因"（哪个 capability / 哪个 buffer / 数组多大）
   在**紧跟的续行**里（同 tag 同 tid）⇒ **只看首行会漏掉最关键那句**。用 `.work/vklayer_ctx.py <tag> <关键字> [前] [后]`
   把原文连上下文打出来（**最少加工最少出错**；本轮 `vklayer_msgs.py` 第一版就因为 logcat 前缀正则写错、续行没拼上而"看起来什么都没有"）。
2. **VUID 名字中间可以有 `-`**（`VUID-vkCreateDevice-ppEnabledExtensionNames-01387`）⇒ 正则别写 `VUID-[A-Za-z0-9_]+-\d+`
   （那样**一种都匹配不到**，而"匹配不到"与"没有报错"长得一模一样 —— 第 ⑨ 条"判据本身要能回答题目"的又一例）。
3. **总数相同 ≠ 内容相同**：`pCode-08740` 是**每个 shader module 报一次、只报第一个未满足的 capability** ⇒
   修掉一条会改报另一条 ⇒ **必须按 capability / extension 名逐项对比**（`.work/vklayer_cap_diff.py`）。

**离线核对层点名的东西**（不必上设备，`.work/spv/*.spv` 就够）：

| 脚本 | 问什么 | 本轮读数 |
|---|---|---|
| `vklayer_vuid_check.py` | 每份 `.spv` 声明了哪些 `OpCapability` | 6923 份都带同一套（`Shader`/`Float64`/`GroupNonUniform*`/`ImageBuffer`…）⇒ **是"声称"，不是"使用"** |
| `vklayer_builtin_check.py` | `OpDecorate … BuiltIn <值>` 用了哪些内建变量 | **1839 份用 `BuiltIn 4425` = `gl_BaseInstance`**（`BaseVertex`/`DrawIndex` 0 份） |
| `vklayer_fp64_check.py` | 有没有真的声明 64 位类型 / 算术 | **0 份**（`OpTypeFloat(64)` / `OpTypeInt(64)` 都是 0）⇒ `Float64` 报错是噪音 |

⚠ **`builtin_check` 的已知局限**：它只看 `OpDecorate`，**不看 `OpMemberDecorate`**（结构体成员的 BuiltIn，比如
`gl_PerVertex` 里的 `ClipDistance`）⇒ 层报"ClipDistance 数组 8 + CullDistance 1"而本脚本报"0 份"就是这原因 ——
**"脚本说没有"不等于"真的没有"，先看它的覆盖范围**。
