# 安卓图形层重写：推翻「同种架构可照搬」，改为 Vulkan 原生的显式实现

> **这份文档是干什么的**：把安卓支线上一版的口径——「这套架构本来就是照着『换一个平台』设计的，要换的只是
> 宿主与图形层里面对平台的那一侧」——**正式推翻**，并把取代它的那一套**写清楚**：安卓图形层不再是对
> `nvn_mtl.m`（Metal）的逐类翻译，而是**按 Vulkan 的语义重新实现**。

> **不推翻什么**：安卓这条路本身没有走不通。宿主复用 ≈95%、着色器链产出 SPIR-V、RomFS/存档/触摸逻辑全部
> 成立（`docs/ANDROID_PLAN.zh-CN.md` §三·探路 A / 探路 B 的实测读数）。被推翻的只有一句：「图形层也只是换 API」。
>
> **口径来源**：全部事实取自仓库代码与真机日志，逐条标了位置。凡属推断而非实测的，文中一律写明「推断」。
>
> **基线**：分支 `android`，`d12e49c`（M3-3f 收尾；其前 `0331e5f` = M3-3f、`58aaec9` = M3-3e 续收尾）。
> 与其冲突处，以 `docs/ANDROID_PLAN.zh-CN.md` 的「七、下一步」「八、进度记录」为准（那是逐轮更新的正本）。
> **本页 §十一**是把 §四~§九 的规格钉成"分几步做、每步判据是什么"的那一层：里程碑 **N0~N6**（与 `M0~M4` 并列不重号），
> 其中 **N4 顶替 M2 那条一直没过的验收**。

## 一、被推翻的是哪句话

三处原话（一句比一句具体）：

| 出处 | 原话 |
|---|---|
| `README.zh-CN.md:265` | 「安卓手机用的是同一类处理器，游戏程序同样可以原生执行，这条路完全走得通：**要换的只是宿主和图形层对接的那一侧**。」 |
| `docs/ANDROID.zh-CN.md:9` | 「**技术上可行。** 这套架构本来就是照着「换一个平台」设计的……要换的只是宿主与图形层里面对平台的那一侧。」 |
| `docs/ANDROID_PROGRESS.zh-CN.md:48` | 「复用原则：**不重写游戏逻辑**，复用现有宿主；只替换「面向平台」的两侧：前端与图形后端」 |

**它错在哪**：前半句（宿主可复用）是**实测成立**的——探路 A 用一次编译量出 87 个编译单元里 **56 个零改动**、
31 处平台差异都有机械对应物。但这句话把「宿主可复用」**外推**成了「图形层可照搬」，而这两件事的难度不在一个
量级：

- 宿主是 **POSIX/C 的平台差异**：`st_mtimespec` → `st_mtim`、`clonefile` → 递归拷贝、CoreAudio → AAudio。
  这类差异是**替换调用**，逻辑与语义不动。
- 图形层是 **平台语义差异**：Metal 的「主机指针就是缓冲」「写完就是可见」「小提交便宜」在 Vulkan 上
  **没有对应物**，必须**用别的结构把同一件事重建出来**。替换调用换不来语义。

一句话：**宿主可复用，图形层不可照搬。**

## 二、三条地基假设，逐条证伪

安卓图形层的全部实现都压在三条来自 iOS 的假设上。下面每条给「iOS 上为什么成立」→「安卓上拿什么替代」→
「替代方案被什么读数证伪」。

### 假设 1：客体地址空间可以整体换成 GPU 内存（指针即缓冲）

**iOS 上为什么成立**：Metal 用 `newBufferWithBytesNoCopy` 把任意主机指针包成 `MTLBuffer`。游戏的内存池
（顶点、索引、常量、贴图）因此**不需要搬运**，GPU 直接读 CPU 写的那份内存。

**安卓上拿什么替代**：Vulkan 没有等价物。最接近的 `VK_EXT_external_memory_host`——**两台真机都实测没有**
（`vk_hostmem_probe`，读数 `.work/logs/probe-*`）。于是 `dm/android/vk/vk_region.c` 造了一套装置
（`:1-18` 的文件头自述）：**分配可导出的 Vulkan 内存 → `vkGetMemoryFdKHR` 取 fd → `mmap(MAP_FIXED)`
压回客体地址**（甲案），甲案不可用时退 `AHardwareBuffer`（AHB 支路）。

**被什么证伪**（四条，全是真机读数）：

| # | 读数 | 位置 |
|---|---|---|
| 1 | **不可移植**：Mali-G610 MC6 上不透明 fd 两种能力都没有、dma-buf 只有 IMPORTABLE ⇒ 甲案不存在，第二台 `建载体缓冲失败（256 MB）`，堆/别名区各 0 MB，启动即 `SVC 越出 alias 区` + `Break#1 0xd401` | `vk_region.c:59-66`、`ANDROID_PLAN`「M3-3d」 |
| 2 | **替代品会打崩内核**：AHB 支路把 ~4 GB 铺成客体堆后，第二台 `kernel_panic` **重启三次**（10:45:49 / 10:46:38 / 10:47:49）；分级复量把触发点收窄到**原子/独占访问**——`LDADDAL` 当场把宿主打成 `SIGBUS`，而普通读写不会。⇒ **GPU-only 用法位的内存没有原子语义**，可是**客体一拿到堆就要用互斥/引用计数** | `vk_region.c:79-98`、`ANDROID_PLAN`「M3-3e」 |
| 3 | **大池子根本装不进去**：4 GB 缓冲带 `STORAGE_BUFFER` 建不出来（撞 `maxStorageBufferRange`）⇒ 退化成"只带传输位"并计数（`g_pool_small`）——**那种池子里的顶点/纹理目前上不了 GPU** | `nvn_vk.c:55-61, 115` |
| 4 | **覆盖不全就报红**：池子只要落在换轨范围之外（栈、预留段就落在外面）就不能成为 GPU 缓冲，代码要求 `g_pool_no_region` 恒为 0——**也就是要求"客体所有池子都在我们铺过的那几段里"** | `nvn_vk.c:90-100` |

**这条设计其实已经被自己的文档判过死刑**：`ANDROID_PLAN.zh-CN.md:393` 写着「**所以「把池子指针直接包成缓冲」
这条路在 Vulkan 上不通，设计必须改。**」——但「改」被推迟了，接下来的 19 轮真机实验（M3-2k → M3-3e）都在
这个前提上做排查。

### 假设 2：CPU 写完，GPU 就能看到（隐式一致）

**iOS 上为什么成立**：Metal 侧的代码里**根本没有 flush/invalidate 这个概念**——Apple 统一内存 + 命令缓冲
的隐式依赖排序把它藏起来了。

**安卓上拿什么替代**：没有替代。实测（全目录检索）：

- `dm/android/vk/` 里 **0 处** `vkFlushMappedMemoryRanges` / `vkInvalidateMappedMemoryRanges`；
- `nvn_vk.c` 里对池内存「CPU 写 → GPU 读」**一次定向 barrier 都没有**（barrier 只用在图像布局转换与上传）；
- 一律按 `HOST_VISIBLE | HOST_COHERENT` 申请，靠"提交顺序"顶。

**为什么这不够**：`HOST_COHERENT` 只承诺"host 侧看到的内存是一致的"，**不承诺 GPU 能看见 CPU 刚写的字节**。
两者之间的可见性必须由 **barrier / 依赖**建立。这不是可选的优化，是 Vulkan 内存模型的要求。

**被什么证伪**：卡点 A 的形状。真机读数：每轮约 40 万次绘制、78~84 条管线、**零失败**、零报错，而**能读回来的
颜色目标全是零**（`M2` 第 14 步、`M3-2m` 逐级读 33 张 0 次有内容）。「命令都成功、结果什么都没写进去」正是
可见性缺失的典型形状。

> 注意口径：这**不**等于"卡点 A 已确诊"。它说明的是——**在假设 2 之下，卡点 A 无法被排除**；19 轮的告警清零
> （绑定号、UBO 槽号、texel buffer、深度测试、行距）都在"GPU 已经看到 CPU 写的数据"这个前提下做，而这个前提
> 在安卓上从未被验证过。

### 假设 3：Metal 的提交节奏可以逐个 op 平移（每帧大量小提交）

**iOS 上为什么成立**：Metal 的命令缓冲提交之间有隐式排序，小提交便宜；`nvn_mtl.m` 的结构直接平移过来。

**安卓上的实况**：8 槽轮转 + 每槽一条命令缓冲 + 每槽一个栅栏 + **队列锁**（`vk_queue_lock`），并且大量
`vkQueueWaitIdle`：

- `mtl_drain` / `mtl_finish`（`nvn_vk.c:172-173`）；
- 上传收尾 `one_end_on`（`vk_tex.c:519-541`）；
- 读回 `grab_ser_locked`（`vk_tex.c:1167, 1183`）——注释还明确写着"同苹果侧截图前那次 `mtl_finish_gpu`"。

**被什么证伪**（ftrace 真机读数，`ANDROID_PLAN`「M3-3c」）：

- 生病轮 **op/帧 96~107**、每轮 **2~4 条 10.1~11.8 秒长等**；健康轮 op/帧 1276.5、零长等 —— **同一条代码路径**；
- 停摆时 `kgsl_hwsched` 的最后阻塞是 **`adreno_hwsched_work+0x37c`「正常等新活」**，而我方线程最后一批阻塞
  **全是读文件** ⇒ 「**提交早已发出、只是没人执行**」；
- 恢复瞬间 = **`gmu_f2h` 中断 + GPU/GMU 时钟与总线重编程**；整条 GPU/显示通路（含 SystemUI、composer HAL）
  一起睡又一起醒。

⇒ 这不是"某个调用写错了"，是**驱动在"每帧上千次微提交 + 没有依赖表达"下的调度结果**。它不像 bug 那样有
根因可以逐轮排除——所以它才表现为**一直陷入调试循环**。

### 三条假设 → 全部症状的映射

| 症状（真机读数） | 落在哪条假设 |
|---|---|
| 画面全零（40 万次绘制、零失败） | 假设 2（可见性从未建立） |
| 每轮约 10 秒 GPU/显示通路停摆 | 假设 3（微提交节奏） |
| 设备丢失 `VkResult -4`（粘的，131 条上传失败） | 假设 2 + 3 |
| 第二台启动就停在内存换轨 | 假设 1（甲案不可移植） |
| 第二台 AHB 支路内核 panic | 假设 1（替身没有原子语义） |
| 启动约 25% 崩溃（`CRASH sig=11 … pc=libc.so+0xd6b18`） | 假设 1 的下游（池/绑定的边界，推断） |
| 写保护脏页跟踪在安卓上**完全失效** | 假设 1：缺页钩子靠 `crash.c` 的 `is_write` 判读写，而安卓 `DM_UC_HAVE_ESR=0` ⇒ `is_write` 恒 0 ⇒ `nvn_dirty.c:82` 直接返回 0；且 `dm/android/**` 无一处引用 `nvn_dirty_*` |

## 三、结论：不是一串 bug，是一个不成立的地基

上一版的口径让人以为：卡点 A、卡点 B、设备丢失、启动崩溃、第二台跑不起来，是**五个待排的 bug**。
按本文的口径，它们是**同一个地基在五个位置上的开裂**：

> **iOS 图形层靠平台免费得到的三件东西——「指针即缓冲」「写完即可见」「小提交便宜」——在 Vulkan 上都不存在，
> 而安卓侧的实现假定它们存在。**

在这套地基上继续排查，是**把正确的排查方法用在了错误的前提上**：读数可信（`DM_GFX_PROBE` 已自证读回
分毫不差）、排除面清楚（锁、睡眠、诊断开关、上传对象、前端上屏路都已被单变量 A/B 臂否掉）、纪律严格
（一次一变量、判据写进文档）——**但每一次排除，都只是在给一个不成立的前提补一个补丁**。这就是"调试循环"
的形状：**排除得越干净，越说明问题不在这条列表里。**

## 四、取代它的一套：Vulkan 原生的显式实现

新的安卓图形层不追求"把 `nvn_mtl.m` 翻译过来"，只追求一件事：**把 iOS 上免费得到的三件事，在 Vulkan 上
显式地买回来**。四条原则，每条都对应上面的一条假设。

### 原则 1（对假设 1）：客体池不再"变成" GPU 内存，而是**有影子、有后备资源**

- **客体池 = 宿主 mmap 的普通内存**（`PROT_READ|PROT_WRITE`，匿名）。语义是普通内存：原子、`mprotect`、
  页保护、引用计数**全部天然成立** ⇒ 第二台的"AHB 原子访问 SIGBUS / 内核 panic"这一类问题**从根上不存在**。
- 每个池对应一块或多块 **GPU 后备 `VkBuffer`**（`DEVICE_LOCAL`）。**按块切分**（例如每 256 MB 一块）就绕开了
  `maxStorageBufferRange` ⇒ 4 GB 池也能全功能建出来，不再有 `g_pool_small` 那种"池内数据上不了 GPU"。
- **两类池，按用法选**：
  - **上载型**（顶点/索引/常量/贴图）：CPU 写影子，提交时把脏区间搬进后备资源；
  - **往返型**（渲染目标/计算输出/计数器）：GPU 写后备资源，CPU 读之前显式回读。
- **零拷贝不是地基，是可选的快路**：当设备支持"可导出不透明 fd"（Adreno 有、Mali 没有）时，允许把某些
  池"钉"到 GPU 内存上省掉拷贝；**但它只是快路，正确性不依赖它**。这一条直接消灭"第二台跑不起来"。

> 代价要说在前面：默认路径**多一次搬运**。所以配套要求是"只搬脏区间 + 块粒度"，不是整池搬运；
> 且真机第一步就要量出"每帧搬运字节数"，作为后续优化的基线（见 §七）。

### 原则 2（对假设 2）：可见性显式建立——脏记账 + 屏障 + 定向栅栏

- 每块池内存有状态：`CPU_DIRTY` / `GPU_DIRTY` / `CLEAN`（分块、按区间）。
- **提交时**：把 `CPU_DIRTY` 且本次会被 GPU 访问的区间，按顺序做
  `vkCmdCopyBuffer`（影子 → 后备）→ `vkCmdPipelineBarrier(TRANSFER_WRITE → 目标访问)`，然后清标记。
- **CPU 读之前**：若该区间是 `GPU_DIRTY`，等**该次提交的栅栏**（不是 `vkQueueWaitIdle`）→ 回读 → 清标记。
- **禁止**"提交完就假设 GPU 看得见"。
- 顺带把安卓侧失效的**写保护脏页跟踪修好**，且修得**不依赖 ESR**：只把页设成 `PROT_READ`
  （允许读、禁止写），则**任何缺页都必然是写**，`is_write` 那一位就不需要了（`nvn_dirty.c:82` 的
  `is_write ? find(...) : NULL` 可以把 `is_write` 去掉）。宿主用系统调用写客体内存那条路
  （`prep_write`）已有对应钩子，保持。

### 原则 3（对假设 3）：帧批提交 + 有界在飞，删掉 `vkQueueWaitIdle`

- **一个「客体提交」= 一次 `vkQueueSubmit`**（这正是 NVN `nvnQueueSubmitCommands` 的语义），命令缓冲内部
  只记不提交。
- **有界在飞**（例如 3~4 槽）：满了就等**最老那个槽的栅栏**（带超时），不再"提交完就等队列空闲"。
- **删除全部 `vkQueueWaitIdle`**：需要等就等**具体栅栏**。它是"设备丢失最灵敏的探针"（`M3-2y`），
  也是让驱动面对大量微提交的元凶之一。
- **前端上屏走同一条队列**（而不是第二条队列 + 队列锁）：用时间线信号量排队，而不是用互斥锁串行。

### 原则 4（对全部三条）：绑定以 SPIR-V 反射为**唯一真源**

现在描述符绑定是"从 `res.json` 猜槽号，猜错了静默错绑"。真机事故记录在案：绑定号 off-by-16 ⇒
管线读的绑定从未绑过 ⇒ 几何塌陷 ⇒ 348k 次绘制、一个像素不落、零报错（`vk_pipe.c:582-586`）。

新方式：`vk_spv.c` 已经从 SPIR-V 读出权威绑定表——**把它变成唯一来源**，`res.json` 只用来**校验**，
不一致就**报红并指出是哪个 binding**，而不是继续跑。这样"绑定号"这一类问题**第一次出现就被点名**，
不再需要 19 轮去人工反查。

## 五、与旧路的关系

| 部分 | 处置 | 说明 |
|---|---|---|
| `dm/host/**`（宿主） | **保留** | 复用结论不变（56 个零改动）。只留住 `__ANDROID__` 分支与 `dm/android/compat/` |
| 着色器链 / SPIR-V / 改写器 / RomFS | **保留** | 与平台无关，6923 个 SPIR-V 直接可用 |
| `dm/gfx/nvn/hle_nvn.c`（NVN 入口、523 槽） | **保留** | 它是"客体 ↔ 宿主"的边界，与图形后端无关 |
| `dm/gfx/nvn/nvn_obj.h`（命令流格式） | **保留** | op 表是客体侧协议，不是 Metal 的私货 |
| `dm/gfx/nvn/nvn_mtl.m`（Metal 实现） | **不动** | iOS/macOS 的正本，继续服务那条线 |
| `dm/android/vk/nvn_vk.c`（照搬结构） | **逐模块替换** | 保留 op 解释器骨架；**提交、内存、同步三块重写** |
| `dm/android/vk/vk_region.c`（mmap 换轨） | **降级为快路** | 不再要求"必须铺成功"；铺不到就走影子路径，只报计数不报红 |
| `dm/android/vk/vk_tex.c` 的上传/读回 | **重写为窗口式** | `vkQueueWaitIdle` 全部换成定向栅栏 + 回读窗口 |
| `gfx_stub_android.c` | **继续按块删** | 原机制不变：实现一块删一条 |
| 探针（`*_probe.c`）、`vk_ops`、等待点转储 | **保留** | 项目最大的方法资产，新地基同样要它们 |

**迁移顺序**（每步都能单独真机验证，不留半步）：
1. 新内存模型（原则 1 + 2）→ 探针自证闭环；
2. 新提交模型（原则 3）→ 量"每帧提交次数 / 长等条数"；
3. 绑定改为反射唯一真源（原则 4）→ 建管线时校验；
4. 接管 `mtl_pool_add` / `mtl_addr` / `mtl_sub_*`；
5. 旧路 `DM_GFX_LEGACY=1` 保留一个版本，能 A/B 对照后删。

## 六、验证闸门（不做完不算过）

新地基必须能过下面五条。**这五条都是可判定的**，不是"看起来好了"：

## 七、代价、风险与「不做」

**代价（诚实写在这里）**：
- 默认路径多一次搬运。**缓解**：块粒度 + 只搬脏区间 + 影子常驻；先量出每帧字节数再优化。
- 往返型资源（渲染目标）多了"回读"这一步。**缓解**：GPU 只在真写过后置脏；读取端做缓存。
- 这套东西比"mmap 压回去"复杂。**缓解**：每一块都有独立探针，先自证再接管。

**风险**：
- **性能可能达不到 iOS 的 60 fps / 3.8 W**。但当前连"画面出得来"都没到，先正确、后快。
- 分块会让"一次大范围拷贝"要跨块拆开。真正的解法可能是"块内连续、跨块拆命令"，需要实测数据定块大小。

**明确不做**：
- 不重写游戏逻辑，不动 NVN 命令流格式，不动宿主。
- 不把"零拷贝"当唯一路径，也不为它继续换设备。
- 不再用"加超时/加保活"掩盖同步问题（plan §10 的口径）。

### 9.2 核心数据结构

```c
/* 池内分块的后备资源：切块是为了绕开 maxStorageBufferRange（4 GB 缓冲带 STORAGE 建不出来的那个坑） */
typedef struct {
    uint64_t     off;   /* 该块在池内的偏移 */
    size_t       size;
    VkBuffer     buf;   /* DEVICE_LOCAL 后备资源 */
    VkDeviceMemory mem;
} vk2_chunk;

typedef struct {
    uintptr_t    lo, hi;        /* 客体池的地址区间（就是宿主 mmap 的那份内存） */
    int          nchunk; vk2_chunk *chunk;
    vk2_dirty    dirty;         /* 脏记账（见 9.4） */
    int          mode;          /* VK2_SHADOW / VK2_PINNED，见 9.8 */
} vk2_pool;
```

**关键不变式**：客体池**永远是普通内存**（`PROT_READ|PROT_WRITE`）。GPU 侧的后备资源是**另一份**内存。
「池在哪儿」与「GPU 用哪块」解耦——这是与旧路（`mmap(MAP_FIXED)` 把两者钉成同一份）最本质的区别，
也正是"第二台跑不起来 / AHB 原子访问 SIGBUS"从根上消失的原因。

> **N1 落地说明（2026-10-16，`vk2_pool.c/.h` 已落地）**：上面这条"永远是普通内存"在代码里的判法是
> **读 `/proc/self/maps`，要求有一段 `rw` 映射把池的 `[lo, hi)` 整段盖住**（有洞或不可读写都不算）——
> 它就是新地基里 `g_pool_no_region` 恒为 0 的**机制**（旧路的前提是"落在我们铺过的换轨区间里"）。
> 两条实机上必须记住的实现细节：① **池地址要先掩掉最高一个字节再和 maps 比** —— 这台机的 `malloc` 返回
> TBI 标记指针（实测 `0xb400000000000000`），而 `mmap` 与 `/proc/self/maps` 都是不带标记的地址；
> ② **它不要求页对齐、也不做任何 `mprotect`**（旧路的两条硬前提都消失了）。块大小取 **960 MB**（§9.9 的读数），
> **块数按池大小算**（4 GB ⇒ 5 块：4×960 MB + 256 MB）。真机读数与两条更正见
> `ANDROID_PLAN.zh-CN.md` §八·N1。

### 9.3 地址反查的契约变化

`vk2_addr(addr, len, VkBuffer *buf, uint64_t *off)`：成功 1 / 失败 0，`*buf` 是 `VkBuffer` 句柄
（与 `nvn_mtl.h` 的约定一致，`mtl_addr` 的调用方不用改）。

**变化**：请求 `[addr, addr+len)` **跨块**时返回 0，并在日志里报"这次访问跨了块边界"（带长度分布）。
调用方（绘制绑定、拷贝、贴图上传）按不可跨块实现——**VB/IB/UBO/贴图的单次访问本来就远小于块大小**，
真正要拆的只有大范围拷贝与整张贴图，逐个加拆分点即可。这块日志是"块大小该定多少"的实测依据。

### 9.4 脏记账与屏障策略

| 事件 | 记什么 |
|---|---|
| `mtl_exec` 的 `COPY_B2B` / `UPDATE_UB` / `COPY_STRIDE` | 目标区间标 **CPU_DIRTY**（保守：整个区间） |
| `BIND_VBUF` / `BIND_UBO` / `BIND_SSBO` / `BIND_TEX` / `BIND_IMG` | 该绑定区间标 **CPU_DIRTY**（保守，先正确） |
| `SET_RT` / `COPY_T2B` / 计算输出 | 目标区间标 **GPU_DIRTY** |
| 提交结束 | 本次提交写过的区间 → GPU_DIRTY；本次搬上去的区间 → CLEAN |

- **粒度**：池内 4 KiB 位图起步（待实测后决定是否放大到 16/64 KiB，以匹配安卓的页大小模式）。
- **写保护（第二阶段，可选）**：把"干净且只被 GPU 读"的页设成 `PROT_READ`。**因为读是允许的，任何缺页
  都必然是写** ⇒ `nvn_dirty.c:82` 那个 `is_write ? find(addr) : NULL` 里的 `is_write` 可以直接去掉，
  安卓缺 ESR（`DM_UC_HAVE_ESR=0`）这件事就不再挡路。宿主用系统调用写客体内存的那条路
  （`prep_write`，经 `dm_guest_write_prep_register` 注册）保持不变。
- **屏障**：上传的每个 run 后插一条
  `vkCmdPipelineBarrier(TRANSFER_WRITE → SHADER_READ|TRANSFER_READ|UNIFORM_READ|VERTEX_ATTRIBUTE_READ ...)`，
  目标访问位按"这段接下来会被当什么用"给（保守给全覆盖，先正确）。

> **N2 落地（2026-10-16）**：本节按此实现（`vk2_dirty.c/.h`）。三条实现细节与真机读数见 §9.5 后面那段
> 「N2 落地说明」：**三态两位位图**（4 GB 池 262144 字节）、**半页竞态只报计数**（随机记账 20000 次命中
> 5225 次）、屏障实测累计 103 条（对应 103 条拷贝）。写保护那一半（第二条，可选）**本轮仍未做**。

### 9.5 上传 / 回读窗口

```c
void vk2_upload_begin(VkCommandBuffer cb, uint64_t frame);
/* 按 CPU_DIRTY 的 run 逐个：memcpy 影子 → 暂存环，vkCmdCopyBuffer(暂存 → 后背)，插屏障 */
void vk2_upload_end(VkCommandBuffer cb);

int  vk2_readback(VkBuffer src, uint64_t off, void *dst, size_t n);  /* 等定向栅栏 → 拷回 → memcpy */
```

- **暂存环**：沿用旧路的做法  （`HOST_VISIBLE|HOST_COHERENT` 环形缓冲），大小按"一帧搬运字节数"实测后定
  （这是新基线的第一个读数）。**N2 已落地 16 MiB 并实测**：512 MB 真搬 = 32 个窗口、127~153 ms ⇒
  **3.3~4.0 MB/ms**（含位图扫描、memcpy、录制、提交、等待），但这个"每帧"的读数要等 N4 的真帧才有。
- **回读**：**不许 `vkQueueWaitIdle`**。等"那次提交的栅栏"（`vkWaitForFences`，带超时）→ `vkCmdCopyBuffer`
  到 host-visible → 再等那条拷贝自己的栅栏 → `memcpy` 到影子。
- 旧路的 `ent_upload`（`vk_tex.c:785`，收尾 `one_end_on` 等队列空闲）与 `vk_tex_grab`（`vk_tex.c:1083`，
  先 `vkQueueWaitIdle`）就是被这两个窗口替代的两个点。

> **N2 落地说明（2026-10-16，`vk2_dirty.c/.h` + `vk2_xfer.c/.h` 已落地）**：上表按此实现，三处必须记下来的：
> ① **三态要两位位图**：CPU/GPU 各一张 1 bit 位图 ⇒ 4 GB 池 **262144 字节**（N0 量的 131072 字节是 1 bit/页 的账）。
> ② **「一条 run 比暂存环还大」要能切**：512 MB 的搬运被 16 MiB 环切成 32 个窗口；切片条件是
> `min(块内余量, 环余量)`，只按块边界切会让"整条 run 大于环"变成整个窗口被拒（N2 第一版就栽在这儿）。
> ③ **半页竞态**（GPU 写过的页被 CPU 部分写）本轮**只报计数不猜**（`hazard_halfpage`，实测随机记账里
> 20000 次命中 5225 次）—— 真正的处理（先回读该页 / 页内字节级记账）留给 N4 的绑定点。真机读数、
> G1/G2 的一问一答与 §9.5 的两处措辞差异见 `ANDROID_PLAN.zh-CN.md` §八·N2。

### 9.6 提交模型

```c
typedef struct { VkCommandPool pool; VkCommandBuffer cb; VkFence fence; uint64_t frame; } vk2_slot;
/* VK2_INFLIGHT = 3~4（待实测：太少会挡帧，太多会压驱动） */
```

- `vk2_sub_begin()`：取一个空槽（**满了只等最老那个槽的栅栏**，不等队列空闲）。
- `vk2_sub_commit()`：`vkResetFences` + `vkQueueSubmit(..., slot->fence)`——**一次客体提交 = 一次 vkQueueSubmit**。
- `vk2_sub_wait(frame)`：等指定槽的栅栏（带超时）。
- **`vkQueueWaitIdle` 出现次数必须为 0**：代码里放一条自检，命中就报红（这是 G4 的判据）。

> **N3 落地说明（2026-10-16，`vk2_sub.c/.h` 已落地；探针 `vk2_sub_probe.c`，第一台四轮）**：本节照此实现，
> 三处要记下来的：
> ① **取槽先"问"再"等"**：`vk2_sub_begin()` 先用 `vkGetFenceStatus` 把已经完成的槽收掉（**这不是等待**，
> 单独计数 `poll_reaps`），还是满的才去等**最老那个槽的栅栏**（带超时）⇒「槽等待率」= 真等待次数 ÷ 取槽次数。
> ② **"3 还是 4"由读数定下来 = 3**：D=1/2/3/4/8 各 24 次、每次 128 MB 的 GPU 拷贝（故意让 GPU 忙起来，
> 否则分辨力不够）⇒ **D=3 → D=4 的每提交耗时变化 -4~+26‰**（四轮全部 < 5%，两轮里 D=4 更慢），
> 而 D=1 是 **7822~13587 µs**、D≥3 稳定在 **4059~4085 µs**（**有界在飞本身就是吞吐**）；D≥3 的最长等待
> **3.48~3.81 ms ≈ 一条提交自己的 GPU 活**（等待是有界的）。注意「长等条数」**不能当否决条件**（GPU 塞满时
> 取槽等一会儿正是设计要的行为），"2 还是 3"的差别在本测试的分辨力之下、留给 N4 的真帧。
> ③ **槽与上传窗口的关系（N4 怎么接）**：`vk2_upload(cb, frame, pool)` 录进**调用方给的 cb**，而暂存环是**一份**
> ⇒ 用 `vk2_sub_note_upload()` 把"这个槽载着上传窗口"标上，**该槽被回收时模块自动 `vk2_xfer_window_done()`**
> （环的存活期 ≤ 槽的存活期）；探针验过"上传 → 回读逐字节等于独立重算的期望 + 交还之后再录一窗被接受"。
> **并且量出一条 N4 待办**：环是**单窗口**的（在飞 3 个槽里只有 1 个能载上传窗口，`contended 2 / uploaded 1`）
> ⇒ **N4 要按槽分环**（或给环做分配器），否则上传会把在飞深度串行化。真机读数与"探针自己两个坑"见
> `ANDROID_PLAN.zh-CN.md` §八·N3。

### 9.8 快路（PINNED）与降级

- `PINNED`：设备支持"可导出不透明 fd"（Adreno 830 有）时，可把某些池钉到 GPU 内存上，省掉搬运。
- **降级规则**：任何一步失败（问不到能力 / 建载体缓冲失败 / 需要原子语义的池）⇒ 该池回落到 `SHADOW`，
  **报计数不报红**。旧路的 `【红】建载体缓冲失败（256 MB）` 在新地基下只是一行【黄】。
- 纪律：**正确性路径不依赖 PINNED**；PINNED 只做性能对照（A/B 臂），不做默认。

2. **读数落盘 + 写进文档** —— 探针读数进 `.work/logs/probe-<串号>-vk2_probe*.txt`；结论写进
   `ANDROID_PLAN.zh-CN.md` 的「八、进度记录」新增一节，并在「七、下一步」回勾；
3. **再接管** —— 探针**在第一台上**过了之后，才把这一块接到回放层上跑游戏（**第二台不使用**：见 §11.5 第 2 条，
   G5 留档待将来）；不过 ⇒ **先修地基，不进游戏**。

两条硬约束：**一次只改一块**（过程中不顺手改别的，旧路保持可退）；**判据不混用**（G1~G5 才是新地基的验收，
旧路那套"健康 / 生病 / 停顿型 / 设备丢失型"只对旧路有意义，见 §9.10）。

### 11.3 新基线要量的六个字段（开工就把尺子立起来）

新地基的"好"不看旧路那套判类，而看下面六个数（从 N0 起每轮记，单独一张表，不与 `ab-readings.tsv` 混）：

| 字段 | 为什么量它 |
|---|---|
| **每帧搬运字节数**（上传 + 回读） | "多一次搬运"这个代价的直接读数，也是块大小与后续优化的依据 |
| **每帧脏 run 数** | 决定脏位图粒度（4 KiB 还是放大）与命令条数 |
| **每帧提交次数** | G4 的判据之一（应当等于"客体提交"次数） |
| **长等条数与最长阻塞时长** | 与旧路唯一可比的那一半读数（旧路生病轮是"每轮 2~4 条 10.1~11.8 秒"） |
| **`vkQueueWaitIdle` 出现次数** | G4 的硬判据，必须为 **0**（代码里放自检，命中就报红） |
| **槽等待率** | `VK2_INFLIGHT` 取 3 还是 4 的依据 |

> **N3 起，六个字段里有"两栏的半格"有了读数（都是机制读数，不是帧读数）**：
> **`vkQueueWaitIdle` 出现次数** —— **N3 的新模块里 = 0**（四轮一致）；**游戏路径上的计数要等 N4**
> （那时新提交路才真的被调用），两者要分清（口径见 `.work/logs/vk2-readings.tsv` 的 N3 行）。
> **槽等待率** —— 机制读数 D=3 = **875‰**（21/24），它只在"GPU 被塞满"的合成测试里有意义；
> 而"**3 还是 4**"已经由 **D=3 → D=4 的每提交耗时变化（-4~+26‰，四轮全部 < 5%）** 定下来 = **3**
> （读数见 `ANDROID_PLAN.zh-CN.md` §八·N3）。其余四个字段（每帧搬运字节数 / 每帧脏 run 数 / 每帧提交次数 /
> 长等条数）没有真帧 ⇒ **留空标"待 N4"**。
